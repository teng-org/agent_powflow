# Chat API 池性能优化与端点实测记录（2026-08-08）

## 1. 结论与适用边界

当前系统作为“单个企业、单套部署、内部员工使用”的智能体后台，核心链路已经具备可用基础：统一登录、知识库、对话、工作流、任务执行、审批、API 池、用量与告警均有实现。若按小规模试运行或受控生产使用，可以进入业务验收。

它仍不等于具备正式 SLA 的完整企业级产品。上线前至少还需完成：生产密钥与 SSO/企业身份接入、容量与并发基准、供应商价格维护、完整备份恢复演练、告警通知闭环、高可用部署、安全渗透测试及业务验收。详细缺口见 `docs/requirements/enterprise-capability-gap-requirements-v1.zh-CN.md`。

## 2. 本次问题定位

历史调用日志中，Embedding 通常约 0.25～0.35 秒；Chat 流式调用常见 10～70 秒，个别记录达到约 244 秒。代码与配置同时存在以下放大因素：

1. 每次上游请求新建 `httpx.AsyncClient`，无法复用 DNS、TCP、TLS 与 HTTP keep-alive 连接。
2. 端点的 120 秒超时是单次网络阶段/读等待限制，不是整个流式请求的墙钟时间上限；持续有数据到达时总耗时可以远超 120 秒。
3. 默认流式输出上限为 4096 tokens，复杂提示词和推理模型可能产生很长响应。
4. 同优先级端点原先严格轮询，快速与慢速供应商获得同等流量；慢端点会直接拉高用户侧 P95/P99。
5. 日志只有总耗时，缺少响应头耗时与首字耗时，无法区分连接、供应商排队和生成速度。
6. Console 原“测试”仅把健康查询写入调试工作台，没有真正请求指定供应商端点。

## 3. 已实现优化

### 3.1 后端

- `LlmClient` 使用进程级异步 HTTP 客户端与连接池，服务关闭时显式释放连接。
- 新增 `chat_stream_total_timeout_seconds`，对每次流式尝试施加真正的墙钟时间上限，默认 120 秒。
- 流式调用日志新增 `response_headers_ms` 与 `first_token_ms`，保留总耗时用于端到端诊断。
- API 池启用延迟感知路由：同优先级端点中，EMA 明显高于最快端点的端点暂不进入常规轮询；无历史数据的端点仍可探索，所有候选异常时仍会回退。
- 新增精确端点探测接口：

  `POST /api/v1/admin/chat/api-pool/{endpoint_id}/probe`

  请求默认最多生成 8 tokens、30 秒硬上限、无重试。Embedding 返回向量维度；LLM 返回响应头、首字、总耗时、可见输出字符数、推理字符数和结束原因，不返回正文、向量或 API Key。
- HTTP 200 但短预算内没有可见正文时返回 `result_status=DEGRADED`，不再误报为完整通过。

相关运行参数：

| 参数 | 默认值 | 作用 |
|---|---:|---|
| `chat_http_keepalive_enabled` | `true` | 复用供应商连接 |
| `chat_stream_total_timeout_seconds` | `120` | 单次流式尝试的墙钟上限 |
| `chat_api_latency_aware_routing_enabled` | `true` | 开启延迟感知候选过滤 |
| `chat_api_latency_routing_ratio` | `3.0` | 相对最快 EMA 的容忍倍数 |
| `chat_api_latency_routing_slack_ms` | `1500` | 绝对延迟容忍余量 |

### 3.2 Console

- Chat 端点明细与实例挂载视图新增“实测”操作。
- 每个端点显示熔断/失败状态、EMA 延迟和最近探测结果。
- 探测过程使用逐端点 loading，避免整页锁死。
- 连接成功但没有可见正文时显示“降级”，提示检查推理预算或模型适配。
- 核心 API 池与可选统计采用隔离加载；单个报表失败不再把整个 API 池误报为 `Failed to fetch`。

## 4. 真实端点结果

实测使用当前数据库中的 9 个 Chat 池端点。每个端点只执行一次固定短请求，LLM 最多 8 tokens、无重试；因此结果主要用于鉴权、连通性、供应商排队与首字基线，不代表长回答吞吐。

| 类别 | 数量 | 实测结果 |
|---|---:|---|
| Embedding | 2 | 均成功，1024 维，约 0.83～0.99 秒；浏览器二次实测约 0.20 秒 |
| SiliconFlow DeepSeek 主回复 | 2 | 均有可见正文；首字约 0.66 秒和 4.49 秒 |
| Qwen 辅助/总结 | 4 | HTTP 连通；3 个约 0.86～0.91 秒，1 个响应头约 18.89 秒；8-token 预算内未产生可见正文，标记降级 |
| DeepSeek 官方主回复 | 1 | HTTP 连通，总耗时约 1.31 秒；8-token 预算内未产生可见正文，标记降级 |

判断：响应慢主要来自供应商排队/冷启动、端点之间显著的延迟差异，以及推理模型在产出可见正文前消耗 token；不是本地数据库或 Embedding 链路主导。连接复用能减少本地握手开销，延迟感知路由能避免持续平均命中已知慢端点，但无法消除上游冷启动。

## 5. 运维建议

1. 主回复池至少保留两个通过“有可见正文”探测的端点；降级端点不要设置更高优先级。
2. 连续观察 24～72 小时的首字、总耗时、失败率与熔断次数，再决定权重和优先级，不能只凭一次探测永久下线。
3. 为每个端点维护真实 `input_per_1k` / `output_per_1k`；当前价格为 0 时，成本报表和预算门禁没有业务意义。
4. 若业务通常要求短答，可在业务验收后把 `chat_stream_max_tokens` 从 4096 下调至 2048 或按场景分级；本次没有擅自改变用户当前输出长度配置。
5. 对推理模型增加供应商级参数适配（如关闭思考或设置 thinking budget）前，先确认各供应商 OpenAI 兼容参数，避免用通用字段造成不兼容。
6. 生产 SLA 场景应增加定时主动探测、P95/P99 指标、Prometheus 告警和供应商故障演练；当前按需探测和 EMA 路由适合单企业试运行，但还不是完整的多区域高可用方案。

# ADR-007：Chat-Plane 强租户约束与越权防护

- 状态：Accepted
- 日期：2026-03-02
- 决策者：Agent Powflow 核心开发组
- 关联：`ADR-003`、`ADR-006`

## 背景
当前系统已引入多租户与强鉴权，但 `chat-plane` 仍存在“前端传参可影响租户范围”的风险窗口。  
在进入 P2（用户体系 + 对话隔离）时，必须把 `chat-plane` 变成“以 token 声明为唯一租户真相源”。

## 决策
在 `chat-plane` 全链路实施强租户约束：

1. 以 `Authorization` 解析出的 `tenant_id` 作为唯一租户上下文。
2. 禁止业务请求体中的租户相关字段覆盖 token 租户。
3. 所有会话、消息、检索、记忆、运行状态查询都必须带 `tenant_id` 条件。
4. 对跨租户访问返回 `403`（明确越权），而不是静默降级。
5. 观测与审计事件中保留 `tenant_id`，用于后续排错和合规追踪。

## 影响范围
- `services/chat-plane/api/*`
- `services/chat-plane/runtime/*`
- `apps/web-app`（前端只传业务参数，不再传/信任租户覆盖参数）
- `apps/debug-web`（调试接口显示 token 租户信息与越权错误）

## 约束与边界
- `PLATFORM_ADMIN` 可跨租户“观测接口”能力应显式实现，不通过普通用户路径隐式放开。
- 若未来支持“租户代理执行”，必须新增受控代理机制，不能复用当前普通 token 流。

## 备选方案
1. 继续沿用“header/request body 提供 tenant_id，后端兼容”  
   - 否决：容易形成绕过点，审计也难保证一致性。
2. 把租户判断完全前置到网关  
   - 否决：当前工程无独立网关统一策略，短期投入大且收益不成比例。

## 验收标准
1. 使用 `tenantA` token 读取/写入 `tenantB` 资源均返回 `403`。
2. 会话列表、消息列表、检索结果、任务运行详情不出现跨租户数据。
3. 调试台可观察到当前 token 的租户上下文和越权拒绝结果。
4. 回归测试覆盖：同租户多用户 + 跨租户用户组合用例。

## 后续任务
1. chat-plane 请求鉴权与上下文注入统一化。
2. 数据访问层按 `tenant_id` 条件强制收口。
3. web-app 与 debug-web 对齐新错误语义（401/403）。
4. 增加最小 E2E 用例验证隔离。

# 产品范围澄清 v1（企业优先 + 快速行业落地）

- 版本：v1
- 日期：2026-02-09
- 适用阶段：MVP -> v1.0
- 关联文档：
  - `docs/requirements/product-vision-v2.md`
  - `docs/decisions/ADR-001-product-scope-v1.zh-CN.md`

## 1. 产品定位（明确版）

本系统定位为：

面向企业，以及个人/小型团队的“知识库 + 工具”为核心的快速 Agent 部署平台。  
核心价值是通过可配置的数据流工作流（Agent Canvas）快速搭建行业 Agent 应用，并支持快速上线、稳定运行、后续扩展与升级。

## 2. 目标用户与使用场景

- 企业客户：需要可治理、可审计、可扩展的行业 Agent 应用平台。
- 小型团队/个人：作为低门槛试用与轻量部署入口。
- 典型场景：
  - 企业知识问答与业务助手
  - 多模态输入（文本/图片/音频）处理
  - 工具调用驱动的流程自动化
  - 行业模板化快速交付

## 3. 前台与后台边界

### 3.1 面向客户的前台

仅提供对话网页（Web Chat UI），承载：

- 用户输入（文本/图片/音频/文件）
- 会话展示与结果反馈
- 引用来源与任务进度可视化

### 3.2 后台管理（拆分为三个面）

1. 传统运维与管理后台：
- 用户、租户、角色权限（RBAC）
- 系统配置、运行统计、审计日志
- 任务监控、失败重试、成本统计

2. AI 能力配置后台（独立前端）：
- 控制前台开放能力（是否启用图片/音频/工具调用等）
- 模型、检索、提示词策略配置
- 按租户/应用进行能力开关与限额

3. 资源设施后台（模块库中心）：
- 模块库管理（Canvas 可用节点/组件）
- 知识库管理（KB、文档、索引）
- 工具库管理（Tool 注册、权限、版本）
- 为 Canvas 提供可复用的基础能力积木

## 4. Agent Canvas 的角色与原则

- Canvas 是编排与管理界面，不是运行时真相。
- 运行时只认 DSL 定义与版本快照。
- Canvas 负责“引流与路由用户输入”，将输入导入可执行工作流。

Canvas 重点能力：

- 定义输入分流规则（文本/图片/音频/文件）
- 定义处理链路（预处理 -> 检索 -> 工具 -> 模型生成 -> 输出）
- 定义知识库选择策略（固定 KB / 条件路由 / 租户策略）
- 定义多模块组合（工具节点、检索节点、模型节点）

## 5. 核心系统分层（实现视角）

1. Presentation 层（Vue）：
- 前台对话页
- 管理后台（可分 Web Admin + AI Admin + Resource Admin）

2. Control Plane（Spring Boot）：
- 用户/租户/权限/配置/审计/任务权威状态
- 面向多端扩展的统一 API 网关能力（后续开放多端）

3. Execution Plane（Python + FastAPI + Celery）：
- 执行 Canvas 对应 DSL
- 承担 AI 流程执行（解析、检索、工具调用、模型推理）
- 实现任务并发执行、状态回传、故障重试

4. Data Plane：
- MongoDB（业务元数据、配置、任务与运行状态）
- Vector DB（向量检索）
- Object Storage（原始文档、解析产物、多模态文件）
- RabbitMQ（异步任务分发）

## 6. 必须实现的关键能力

- 多租户隔离（MVP 为 L1 逻辑隔离，后续可升级）
- 任务管理（Task/Run 全链路状态可见）
- 多进程/多 Worker 执行管理（并发、重试、限流、队列隔离）
- 前后端状态同步（SSE/WebSocket + 可追踪 ID）
- 模块插拔（模型/工具/检索/解析 Provider）
- Canvas DSL 版本化（可发布、可回滚、可迁移）

## 7. 快速上线与升级能力（交付导向）

为满足“快速上线、拓展、升级”，v1 必须具备：

- 模板化交付：行业 Agent 模板可复制部署
- 配置化变更：尽量少改代码，通过配置完成能力调整
- 灰度发布：按租户/应用分批启用新工作流版本
- 回滚能力：工作流版本与模型配置快速回退
- 可观测性：出现问题可快速定位到节点/任务/工具

## 8. 多端 API 扩展要求（后续）

Spring Boot Control Plane 需预留多端接入：

- Web 前端（当前）
- 移动端（未来）
- 第三方系统（开放 API / OpenAPI）

API 设计约束：

- 资源模型稳定（tenant/app/workflow/run/task）
- 认证授权一致（JWT + RBAC + tenant context）
- 幂等与分页规范统一
- 向后兼容的版本策略（`/api/v1` -> `/api/v2`）

## 9. MVP 范围边界（防止过度建设）

MVP 建议“必须做”：

- 企业优先主路径完整闭环（上传文档 -> 建索引 -> 对话问答 -> 任务追踪）
- Canvas DAG 编排 + DSL 发布执行
- 三类后台最小能力可用
- 资源库（模块/知识库/工具库）可支撑业务配置

MVP 暂不做：

- 复杂状态机与循环流
- 复杂计费系统
- 完整离线部署保证
- 强监管认证交付

## 10. 验收口径（Definition of Ready for Build）

当以下条件满足，可进入大规模开发：

- 产品边界明确并冻结（本文件 + ADR-001）
- 每个后台域的职责边界明确
- Canvas DSL 与执行协议明确
- 核心链路的任务状态模型明确
- 多租户与权限策略完成技术评审
